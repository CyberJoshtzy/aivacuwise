## User Authentication (completed and verified end to end)

Implemented in `auth.py`, `schemas.py`, and `main.py`:

- Password hashing uses the raw `bcrypt` library directly (`bcrypt.hashpw` / `bcrypt.checkpw`), not `passlib`. `passlib`'s `CryptContext` was tried first but crashed against modern `bcrypt` (`AttributeError: module 'bcrypt' has no attribute '__about__'`, then `ValueError: password cannot be longer than 72 bytes`) during its internal backend self-test. This is a known unmaintained-passlib compatibility issue. Fix: removed `passlib` entirely from `auth.py` and hash/verify with `bcrypt` directly.
- JWT tokens issued via `python-jose`, signed with `JWT_SECRET_KEY` (stored in `.env`, generated with `secrets.token_hex(32)`), algorithm `HS256`, 8-hour expiry.
- Endpoints:

  - `get_current_user_from_token(token, db)` — helper in `auth.py`, decodes a JWT the same way as `get_current_user` but takes a plain string and returns `None` on failure instead of raising, used for authenticating WebSocket connections.

## Evacuee Location Tracking — Two-Phase Design (decided and partly built)

After discussion, the thesis's tracking concept was refined into two distinct, complementary phases rather than one system:

- **Field tracking** (before and during evacuation, i.e. the person is still at home or in transit to a center): uses a GPS + SIM (cellular) wearable tracker. Real AirTags / Apple Find My style trackers were evaluated and rejected for this role — they depend on Apple's cloud, nearby strangers' iPhones for relay, and have no public API for pulling a tag's location programmatically, none of which fits an offline-first, self-hosted, multi-resident system. A GPS+GSM tracker (own GPS chip + own cellular radio) was chosen instead, since it can report from anywhere with cell signal, independent of home Wi-Fi or nearby phones.
  - Hardware options evaluated: GF-07 (cheap, available now on Shopee PH, confirmed to support SMS-based location queries, but its GT700 protocol is NOT confirmed compatible with Traccar per Traccar's own community forum) vs. Traccar-confirmed devices like the Vjoycar T80 (TK103 protocol, compact/personal form factor, but not confirmed available on PH marketplaces, likely needs AliExpress ordering). Decision: proceed with GF-07 + SMS-based ingestion as the primary path for time/availability reasons; Traccar (self-hosted, free, open-source GPS tracking server, supports 200+ device protocols including GT06/TK103, exposes its own REST API) noted as a future upgrade path if a confirmed-compatible device can be sourced with enough lead time.
  - A commercial vehicle-fleet GPS tracking vendor quote (AST-400 hardware + monthly "Web Tracking Platform" SaaS, ~PHP 299/device/month) was evaluated and rejected: it is vehicle-oriented (overspeeding/idling/parking features, likely hard-wired form factor), its feature list shows no API/webhook access (only human-facing app/web views), and even if an API exists it would create ongoing vendor lock-in and recurring cost conflicting with the thesis's local-first, low-cost design. Kept only as a possible side demo, not the core system.
- **Center tracking** (once the evacuee physically arrives): uses the existing BLE beacon + Raspberry Pi proximity detection design. Confirmed still necessary even with GPS/SIM in place, because GPS does not work reliably indoors (concrete buildings block satellite signal), BLE gives precise checkpoint-level confirmation needed for occupancy/headcount accuracy, BLE requires no cellular network (so it keeps working if cell towers are down or congested during a disaster, unlike GPS+SIM), and BLE is far cheaper/lower-power for tracking someone who is already safely accounted for.
- The two phases hand off naturally: GPS/SIM answers "where is this person right now" continuously (raw coordinates, no concept of arrival), while the existing `checkin_records` table (with its `event_type` field) is what logs the actual timestamped arrival/departure event once BLE detects them at a center entrance. A geofence proximity check (comparing GPS coordinates against each evacuation center's known coordinates) was discussed as a possible future enhancement to auto-flag "approaching center X" ahead of confirmed BLE arrival, not yet built.

**Backend built and verified end to end for this feature:**

- `models.py`: added `tracking_method` column (nullable string, e.g. "sms"/"traccar"/"ble") to the existing `Tracker` class, and a new `GpsPing` class/table (`gps_pings`: id, tracker_id FK, latitude, longitude, source, timestamp).
- `schemas.py`: added `TrackerCreate`, `TrackerOut`, `GpsPingCreate`, `GpsPingOut`.
- `main.py`: added `POST /trackers`, `GET /trackers`, `POST /gps_pings` (hardware-agnostic ingestion endpoint — any future SMS-parsing script or Traccar-polling script will call this same endpoint; async, broadcasts a dashboard update), `GET /gps_pings/{tracker_id}/latest`, `GET /gps_pings/{tracker_id}/history`.
- Verified live: registered a test tracker (`TEST-GF07-004`) assigned to evacuee Juan Dela Cruz, posted a GPS ping (14.5995, 120.9842), and successfully retrieved it back via the latest-location endpoint, and later saw it render correctly on the live dashboard's tracker plot.
- This design deliberately decouples the backend from any specific hardware: whichever tracker is finally purchased (GF-07 via SMS parsing, or a Traccar-compatible device via its REST API), only a small adapter script needs to be written later to call `POST /gps_pings` — no backend changes needed.

## Transfers, Walk-in Registration, and Movement History (completed and verified end to end)

Built together as one batch, since they turned out to be interdependent (see "Occupancy accuracy fix" below).

**Occupancy accuracy fix (important):** the original `GET /evacuation_centers/{center_id}/evacuees` counted an evacuee as present if *any* `check_in` row existed for that center, with no concept of "did they later leave." This meant a transferred evacuee would have shown up at both the old and new center simultaneously. Fixed by rewriting the query to find each evacuee's *most recent* `checkin_records` row (using `id` order, not `timestamp`, to avoid tie-breaking issues) and only counting them as present if that latest row is a `check_in` at the queried center. This logic now lives in a reusable helper, `_get_current_evacuees_at_center(db, center_id)`, shared by the REST endpoint and the dashboard summary endpoint. Verified live: after transferring an evacuee, they correctly disappeared from the old center's list and appeared only in the new one's.

**Transfer endpoint** (shelter-to-shelter transfer with approval tracking, using the existing `transfers` table):
- `POST /transfers` — protected, requires any authenticated user (barangay official or city admin) via `auth.get_current_user`; `approved_by` is set automatically from the logged-in user, not client-supplied. Validates the evacuee, destination center, and (if provided) source center exist; validates the evacuee's latest check-in event actually matches the stated source center before allowing the transfer. On success, creates the `transfers` audit row and also writes a `check_out` event at the source center plus a `check_in` event at the destination center. Async, broadcasts a dashboard update for both the source and destination barangay.
- `GET /transfers` — lists all transfers, most recent first.
- `GET /evacuees/{evacuee_id}/transfers` — transfer history for one evacuee.

**Walk-in / unregistered evacuee support:** added because facial recognition is the primary identification method, but real disasters will have people arriving who were never pre-enrolled. Added `identification_method` column to `evacuees` ("facial_recognition" or "manual", default "manual"). Note for later: the existing pre-registration flow (`POST /evacuees`, used when a barangay official enrolls someone's face ahead of time) should explicitly pass `"identification_method": "facial_recognition"`, otherwise it defaults to "manual" and mislabels pre-registered residents — relevant once the Raspberry Pi enrollment script is built.
- `POST /checkin/walkin` — protected (any authenticated user). Creates the evacuee record and the check-in record together in one atomic transaction (`db.flush()` to get the new evacuee's id before creating the check-in, both committed together). Async, broadcasts a dashboard update.

**Movement history:**
- `GET /evacuees/{evacuee_id}/history` — full chronological list (most recent first) of every `checkin_records` event for that evacuee across every center, reusing the existing `CheckinOut` schema.

**Known gap, noted but not built:** there is still no manual "check someone out" endpoint outside of a transfer (e.g. for a shelter simply closing and sending everyone home). Flagged for a future session if needed.

**Verified live end to end:** registered walk-in evacuee Maria Santos via `POST /checkin/walkin` at center 1, confirmed she appeared in center 1's list, transferred her to center 2 via `POST /transfers`, confirmed she then appeared only in center 2's list, and confirmed her `GET /evacuees/{id}/history` showed all three events in correct order.

## Live Dashboard with WebSocket Updates (completed and verified end to end)

Two design decisions made up front: the dashboard is role-based (a city admin sees every barangay and center; a barangay official sees only their own barangay, enforced server-side in `/dashboard/summary`, not just hidden in the UI), and the live tracker map uses a simple plotted grid of coordinates rather than real map tiles (roads/imagery), since real tiles need a live internet connection to a tile server and the thesis requires the system to keep working offline. Bundling a mapping library like Leaflet was considered but dropped once the plain-coordinate-plot approach was chosen, since no map-tile library is needed at all this way.

**Design approach:** rather than pushing full data diffs over the WebSocket, the socket only pushes a small "something changed" signal (e.g. `{"type": "occupancy_update", "barangay_id": 1}`). The dashboard page reacts by re-fetching `GET /dashboard/summary`, the single source of truth, and re-rendering. This keeps the real-time logic simple and guarantees the displayed numbers can never drift out of sync with the database.

**Backend built:**
- `connection_manager.py` (new file): a `ConnectionManager` class tracking active WebSocket connections alongside the connected user, with a `broadcast(message)` method that filters by role — a `city_admin` connection receives every message; a `barangay_official` connection only receives messages whose `barangay_id` matches their own (or messages with `barangay_id: None`, used for GPS pings, which aren't tied to a barangay in the schema).
- `auth.py`: added `get_current_user_from_token` (see "User Authentication" above).
- `main.py`:
  - `GET /dashboard/summary` — protected, role-filtered. Returns every barangay (all of them for `city_admin`, just the caller's own for `barangay_official`), each with its centers, each center's occupancy/capacity and current evacuee list, plus every tracker with an assigned evacuee and its latest GPS position. Response shape: `{"barangays":[{"id","name","centers":[{"id","name","capacity","occupancy","evacuees":[{"id","full_name","identification_method"}]}]}],"trackers":[{"tracker_id","device_id","evacuee_id","evacuee_name","latitude","longitude","timestamp"}]}`.
  - `WS /ws/dashboard?token=<jwt>` — authenticates via `get_current_user_from_token` (token passed as a query parameter, since browsers can't set custom headers on a WebSocket handshake), closes with code 1008 if the token is invalid, otherwise registers the connection with `connection_manager`.
  - `POST /checkin`, `POST /transfers`, `POST /checkin/walkin`, and `POST /gps_pings` were all converted from sync `def` to `async def` so they can `await manager.broadcast(...)` after committing. This is an accepted tradeoff for a thesis-scale prototype (the underlying SQLAlchemy calls are still synchronous and briefly block the event loop), not appropriate at real production concurrency, but fine here.
  - `GET /dashboard` — serves the dashboard page itself via `FileResponse("static/dashboard.html")`.
- `static/dashboard.html` (new file): single self-contained HTML/CSS/JS page, no external libraries or CDN dependencies at all. Has a login form (posts to `/login`, stores the JWT in `localStorage`, calls `/users/me` to learn the logged-in user's role), a barangay/center occupancy view (progress bar, evacuee list with a badge showing `identification_method`), a live tracker section (plain SVG scatter plot, evacuee-labeled dots, auto-scaled to fit whatever coordinates are present, with a fixed small padding window when there's only one point), a connection-status badge ("live"/"offline"), and a WebSocket client that reconnects automatically after 3 seconds if the connection drops.

**Setup note for later sessions:** the `websockets` Python package is required in the venv for uvicorn to support `ws://` connections at all (`pip install websockets`, run with the venv activated — a bare `pip install` outside the venv fails with `externally-managed-environment` on this Ubuntu 24.04 install).

**Verified live end to end:** confirmed `GET /dashboard/summary` returns correctly filtered, accurate data; confirmed the WebSocket pushes an `occupancy_update` message immediately after a check-in (tested first with a standalone Python listener script before building the page, to isolate the backend from frontend concerns); then opened `http://192.168.100.200:8000/dashboard` in Firefox, logged in as `cityadmin`, and confirmed the occupancy cards, evacuee lists, and tracker plot all rendered correctly; finally, with the dashboard page left open and untouched, triggered a new walk-in check-in from a terminal and confirmed the page updated itself within about a second, occupancy count and evacuee list both changing live with no manual refresh, and the "live" status badge stayed connected throughout.

**Not yet tested:** the barangay-official-only filtered view (only one barangay exists in the test data right now, so there's nothing yet to filter out — would need a second barangay to meaningfully verify the role-based restriction is actually enforced server-side rather than just trusted to work).

## Household / Family Registration (completed and verified end to end)

Prompted by a review of BilisLikas 1.0's (the prior thesis group's) barangay-level kiosk screenshots, which registered evacuees as family units rather than one at a time. Design decisions confirmed with the user: keep family/household grouping, identify members by facial recognition plus a walk-in fallback (no RFID, unlike the prior thesis), and this feature is meant to eventually run from a Raspberry Pi kiosk at the barangay level, not the city-wide admin dashboard.

**Backend built:**
- `models.py`: added `household_id` (FK to `households.id`, nullable) and `is_head_of_family` (Boolean, nullable, default False) to the `Evacuee` class; added a new `Household` class/table (`households`: id, registered_barangay_id FK, head_of_family_evacuee_id FK to evacuees, nullable, created_at).
- `schemas.py`: added `HouseholdMemberCreate` (full_name, birthdate, sex, address, contact_number, is_head_of_family), `HouseholdCreate` (registered_barangay_id, members), `HouseholdMemberOut` (id, full_name, is_head_of_family, identification_method), `HouseholdOut` (id, registered_barangay_id, head_of_family_evacuee_id, created_at, members), `HouseholdMemberStatus` (evacuee_id, full_name, is_head_of_family, current_center_id, current_center_name), `HouseholdStatusOut` (household_id, members).
- `main.py`: added four endpoints, all protected (require an authenticated user):
  - `POST /households` — validates the barangay exists, the members list is non-empty, and at most one member is marked `is_head_of_family`. Creates the `Household` row, flushes to get its id, then creates each member as an `Evacuee` row tagged with that `household_id` and `identification_method="facial_recognition"`, flushing each to get its id. Sets `head_of_family_evacuee_id` on the household from whichever member was marked head, then commits everything together.
  - `GET /households/{household_id}` — fetches a household with its members, 404 if not found.
  - `GET /barangays/{barangay_id}/households` — lists every household registered under a barangay, each with its members attached.
  - `GET /households/{household_id}/status` — for each member, looks up their latest `checkin_records` row (same "latest by id" pattern used elsewhere) and reports their current evacuation center, or null if they haven't checked in anywhere yet.
- `CheckinCreate` schema fields (confirmed via `schemas.CheckinCreate.model_fields.keys()`): `evacuee_id`, `evacuation_center_id`, `event_type`. `WalkinCheckinCreate` fields: `full_name`, `birthdate`, `sex`, `address`, `contact_number`, `registered_barangay_id`, `evacuation_center_id`.

**Error hit and fixed during this build:** the first patch script (`fix_households.py`) correctly updated `schemas.py` and `main.py` but silently failed to update `models.py`, because its search-anchor string itself contained a literal `__tablename__ = "evacuees"` (a double-underscore sequence), which is exactly the pattern flagged in Known Quirks item 1 as unsafe to type even inside a fix script. The anchor got corrupted on paste into the terminal and never matched, so `models.py` was left unpatched while the other two files succeeded. Fixed by rewriting the script (`fix_models_households.py`) to anchor on an underscore-free line (`identification_method = Column(...)`) instead, and to build the new `Household` class's `__tablename__` line programmatically inside the script's own source (`dunder = '_' * 2`, then string concatenation) rather than typing it literally.

**Verified live end to end:** registered household id 1 with two members via `POST /households` — Roberto Santos (evacuee id 5, marked head of family) and Elena Santos (evacuee id 6); confirmed `GET /households/1`, `GET /barangays/1/households`, and `GET /households/1/status` all returned correct data; checked Roberto in via `POST /checkin` and confirmed status updated correctly.

**Second pass (arrival-first redesign):** the user asked for a full rework of the layout and flow, deliberately distinct from BilisLikas 1.0's screens. Every path ends on a "Done" confirmation screen that resets back to idle. Occupancy detail and a Staff Menu (logout, "Change Assigned Center" to redo Kiosk Setup) became secondary links instead of equal-weight buttons.

**Hardware correction:** the Pi actually in hand is a **Raspberry Pi 4** (confirmed repeatedly by the user across this session), not a Pi 5 as this log's project framing originally assumed. **Getting SSH and the account working (the hard part):** Raspberry Pi Imager's own OS Customisation UI proved unreliable across three separate flash attempts on this system (a missed/misclicked "Use OS customisation?" confirmation dialog, then an intermittent "Cannot open storage device" write failure caused by the SD card still being mounted from GUI file-browser inspection, then a write that reported success but had only partially applied). The actual mechanism Imager uses for a customized image is a generated `firstrun.sh` script triggered by a `systemd.run=` kernel parameter appended to `cmdline.txt` — not the stock `user-data`/`meta-data`/`network-config` files (unused stubs present on every image regardless of customization) and not a `custom.toml` file either. After three failed attempts, customisation-via-Imager was abandoned in favor of the legacy manual method, which proved reliable: writing an empty `ssh` file (enables the SSH service every boot) and a `userconf.txt` file containing `username:password_hash` (SHA-512 crypt, via `openssl passwd -6`) directly onto the boot partition. **Important caveat discovered the hard way:** the account-creation half of this only runs on a card's genuine first-ever boot — if a card has already booted once (even plain/uncustomized), adding `userconf.txt` afterward and rebooting will NOT create the account, because the firstboot service is gated to run once and its marker is already consumed. The `ssh` empty-file trick is not gated this way and works every boot, which is why SSH kept becoming reachable while login kept failing until a genuinely fresh, never-before-booted card was used. Final working values: hostname `bilislikas-pi`, username and password both `ianpogi123`, reachable at `192.168.100.23` over Ethernet (Wi-Fi country set to PH and rfkill-unblocked, but Wi-Fi credentials not yet configured — Ethernet is the current connection).

**Dependency installation — the aarch64/piwheels gap (important for any future from-scratch Pi setup):** this Pi runs the 64-bit ("aarch64") build of Raspberry Pi OS with Python 3.13 (Debian trixie). `pip`'s config already points at piwheels (`/etc/pip.conf`, `extra-index-url=https://www.piwheels.org/simple`), but **piwheels only publishes prebuilt wheels for 32-bit ARM (armv6l/armv7l), not aarch64**, for both `dlib` and `opencv-python`. Installing either directly on this Pi would silently fall back to a slow, memory-heavy from-source compile. Fixes used, both confirmed working:
- `dlib`: install `dlib-bin` instead of `dlib` (`pip install dlib-bin --break-system-packages`) — a community-maintained package that ships the same `dlib` importable module as a prebuilt manylinux aarch64 wheel (confirmed working for Python 3.13). Then install `face_recognition` itself with `--no-deps` (`pip install --no-deps face_recognition==1.3.0 --break-system-packages`) so pip doesn't try to re-resolve and rebuild plain `dlib` as a dependency, followed by its other, lighter dependencies (`Click`, `Pillow`, `face_recognition_models`) installed separately.
- `opencv-python`: do not pin the old `4.9.0.80` used in earlier drafts of the client scripts; a recent, unpinned `opencv-python` has official manylinux aarch64 wheels directly on PyPI (uses the `cp37-abi3` stable ABI tag, so it works across Python versions including 3.13 without needing a version-specific build).
- `numpy`: do **not** pin `numpy<2` on this Pi. That pin was written for an earlier, older Python version and numpy 1.26.x does not support Python 3.13 at all — attempting it triggers a source build that will not succeed. A recent numpy (already present as a system package, 2.2.4, on this install) works fine with `face_recognition`.
- `face_recognition_models` is a large (~100 MB) pure-Python data package; a slow/flaky connection can interrupt the download partway — `pip install --resume-retries 5 face_recognition_models --break-system-packages` resumes rather than restarting from zero.
- Full working install sequence, in order: `pip install dlib-bin --break-system-packages`, then `pip install --no-deps face_recognition==1.3.0 --break-system-packages`, then `pip install Click Pillow face_recognition_models --break-system-packages`, then `pip install numpy opencv-python "requests==2.31.0" --break-system-packages`.

This discards stale queued frames and keeps only the newest one, bringing the preview much closer to real time.

## Known Quirks to Remember

1. **Double-underscore corruption — confirmed to affect actual file writes, not just chat display, and confirmed again to affect fix-script anchors, not just displayed code.** The user's typing/clipboard environment can corrupt double-underscore sequences (e.g. `__tablename__` becomes `_tablename_` or even loses all underscores entirely) when pasting code from chat into the terminal/editor, when terminal output is copied back into chat, when a `python3 -c "..."` fix command containing literal `__tablename__` is pasted into the terminal and executed, AND when a patch script's own *search anchor* (not just the code it's replacing) contains a literal double-underscore string. The same class of corruption has also been observed dropping other short tokens entirely (a colon-and-number pair, a space) when raw curl/JSON output was pasted back into chat — the risk isn't unique to underscores, it's short tokens in general during clipboard transfer in either direction. **Most reliable fix method found:** never write two underscore characters adjacent to each other anywhere in any command, script, or anchor string sent to the user. Build the string programmatically instead, e.g. `u2 = '_' * 2; target = u2 + 'tablename' + u2`, and verify success with a plain numeric count (`content.count(target)`) rather than a visual/repr check. Prefer writing multi-file changes as a single Python script via a quoted heredoc (`cat > fix.py << 'PYEOF' ... PYEOF`) run from the terminal over having the user manually paste code into VS Code. For binary files (images, fonts), don't pipe them through the terminal at all — have the user save them directly via the GUI file manager instead (see "Barangay Kiosk UI" above), or transfer via `scp`/zip download as established in the "Raspberry Pi Client" section above.
2. **Unsaved VS Code files and Auto Save**: a major source of "phantom" bugs — editing in VS Code without saving (dot on tab instead of X) means terminal commands and server restarts silently use the old on-disk version. The reverse is also a risk: if VS Code's Auto Save is on and a stale/broken version of a file is still open in the editor, it can silently re-save over a fix just applied from the terminal a moment later. **Fix/reminder**: after any multi-file edit, save explicitly (Ctrl+S or Ctrl+K then S) and check tab dots; if a fix was just applied from the terminal, let VS Code reload/revert from disk rather than saving its own in-memory version over it, and consider turning off Auto Save (File menu) during active troubleshooting sessions.
3. **(Mostly solved by the systemd service, see above: the server no longer depends on a terminal tab. The notes below apply only if uvicorn is ever run by hand again.)** **Port 8000 already in use**: recurs when restarting uvicorn after a code change if the previous process wasn't fully killed. Standard fix: `sudo fuser -k 8000/tcp`, wait a moment, then restart. **Important correction**: this command must only be run in the terminal tab that is actually restarting the server — running it in a different tab while the server is freshly started elsewhere will kill that just-started process, producing a plain "Killed" message with no error and no dmesg/systemd-oomd log entry. Note also that HTML-only edits (like the kiosk redesign and rebrand) don't need a server restart at all, since `FileResponse` reads the file fresh on every request; only changes to `.py` files require one. The server also does not stay running between sessions on its own — it needs to be manually restarted (`cd ~/aivacuwise && source venv/bin/activate && uvicorn main:app --host 0.0.0.0 --port 8000`) each time before the Pi client scripts or dashboard will work, this has caused repeated "Connection refused" confusion when picking work back up. **Recurred again this session**: the kiosk showed "Unable to connect" because the server had never been started in the terminal tab being used that day (that tab had only run `git push`/`unzip`/`pip install`); fixed by starting uvicorn in a fresh, dedicated tab.
4. Server must run in one dedicated terminal tab and stay untouched; curl/testing commands go in a separate tab. With many unlabeled "bash" tabs open in VS Code's terminal panel, it's easy to lose track of which is which — rename tabs early (right-click → Rename) to something like "server" and "testing" to avoid confusion. **This confusion extends to the laptop-vs-Pi split now that the Pi is part of the workflow**: the user repeatedly ran laptop-only commands (backend `cd`/`scp`/`find`) inside the Pi's SSH session prompt, and vice versa. The prompt itself is the reliable tell — laptop is `ian@ian-Lenovo-V310-15IKB`, Pi is `ianpogi123@bilislikas-pi` — worth checking before running any command once both a laptop terminal and a Pi SSH session are open at the same time. This extends a third way once the Pi has its own physical monitor: a command meant for the Pi's own local desktop terminal (needed for anything involving `cv2.imshow`, since that needs a real `DISPLAY`) fails differently (a Qt/`xcb` display error) if accidentally run from an SSH session into the Pi instead.
5. IP addresses and URLs get auto-wrapped in markdown link syntax when copied from the terminal into chat — treat this as a display artifact, not an actual config error.
6. **Shell variables (e.g. `export TOKEN=...`) do not carry over between terminal tabs, and do not survive activating the venv fresh in a brand-new tab.** Running a curl (or python) command with `$TOKEN` in a tab where it was never exported produces `{"detail":"Could not validate credentials"}` — this recurred more than once across sessions. Re-export in the tab actually being used, or just log in again; JWTs also expire after 8 hours, so an old exported token from a previous session won't work either.
7. **Forgotten password recovery (local dev database only)**: since bcrypt hashes can't be reversed, a forgotten user password was reset directly through the database rather than the API, using the app's own hashing function for consistency: `python3 -c "from database import get_db; import models, auth; db = next(get_db()); user = db.query(models.User).filter(models.User.username == 'cityadmin').first(); user.password_hash = auth.get_password_hash('NEW_PASSWORD'); db.commit()"`. This is only appropriate because the database currently holds test data with no real evacuee information at stake — flagged as a discussion point for the thesis's security section (a real deployment needs a proper reset flow, not direct database edits). Current test password is `ChangeMe123!`.
8. **`pip install` outside an active venv fails** on this Ubuntu 24.04 install with `error: externally-managed-environment` (PEP 668). Always `source venv/bin/activate` first (prompt should show `(venv)`) before any `pip install`. On the Pi, the equivalent flag is `--break-system-packages` (no venv is used there, since it's a single-purpose edge device script, not the multi-project laptop).
9. **Browser downloads of a repeatedly-updated file don't overwrite by default**: sending an updated `bilislikas_pi_client.zip` more than once in the same conversation resulted in the browser saving `bilislikas_pi_client(1).zip`, `(2).zip`, etc. in `~/Downloads` rather than replacing the original, and a plain `find ~ -iname "bilislikas_pi_client.zip"` would then match the *old* one first. Fix: sort by modification time and take the newest — `ls -t ~/Downloads/bilislikas_pi_client*.zip | head -1` (or `find ... -printf "%T@ %p\n" | sort -n`, taking the last line) — rather than searching by exact filename alone. The same applies to any repeatedly-resent file, not just this one.
10. **SD card firstboot account creation only runs once ever, per card** — see "Raspberry Pi Client" above. If SSH is reachable but every password (including a blank one) is rejected or the connection closes immediately, suspect a card that already completed a first boot before `userconf.txt` was added, not a typo'd password.
11. **Invisible/hidden-prompt typing issue is not limited to SSH/sudo** — it's a general trait of this user's desktop environment with any hidden-input prompt. When a new tool needs a password/passphrase entered interactively (e.g. `ssh-keygen`'s passphrase prompt), prefer a non-interactive flag that supplies it directly in the command (e.g. `ssh-keygen -N ""`) over letting the tool prompt interactively, rather than waiting to discover the same typing problem recurs.

12. **Firefox caches `app.js`/`app.css` aggressively.** After frontend batch 2 was installed, pages showed the new HTML but the old sidebar ("Soon" tags) because the old `app.js`/`app.css` were cached, even though `grep` confirmed the server had the new files. Fix used: a private window (Ctrl+Shift+P), or Settings > Privacy & Security > Cookies and Site Data > Clear Data (cached files only). Planned permanent fix: version query strings on the links (e.g. `app.js?v=3`) in the next frontend batch.
13. **Downloaded zips from chat must actually be saved first.** `ls -t ~/Downloads/<name>*.zip` failed because the file cards had not been downloaded yet; `find / -iname "*batch2*.zip" 2>/dev/null` located them once downloaded. Files are saved as `~/Downloads/bilislikas_<part>_batch<N>.zip`.
14. **Running commands in the server tab stopped the server** several times (the tab had to be interrupted to type into it), causing repeated "Unable to connect". Resolved by the systemd service.
15. **A VPN extension is installed in Firefox.** If a local address ever fails while `curl http://127.0.0.1:8000` works, check whether the VPN extension is routing `192.168.100.200` traffic.
